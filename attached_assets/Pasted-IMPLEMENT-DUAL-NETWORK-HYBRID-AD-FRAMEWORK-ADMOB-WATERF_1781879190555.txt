IMPLEMENT DUAL-NETWORK HYBRID AD FRAMEWORK (ADMOB WATERFALL WITH UNITY ADS FALLBACK & MASTER TOGGLE)

We need to implement a resilient, dual-network advertising framework within our Shiba Hit application using Google AdMob and Unity Ads. This system will mitigate the revenue drop from current AdMob ad limits by dynamically routing ad requests based on live network availability and a remote database configuration switch.

STRICT CONSTRAINT: Do NOT introduce any new or unprompted ad placements. Ads must ONLY render within the exact layouts already established in the application (Banner slots, Interstitial breakpoints, and Rewarded claim actions).

Please follow this exact structural architecture layout to implement the feature:

---

### 1. DATABASE SCHEMA CONFIGURATION (PocketBase Setup)
Append a new configuration flag to our global system settings collection (`app_config`):
- Field Name: `force_unity_only`
- Type: `bool` (Boolean)
- Default Value: `false` (Keeps Hybrid Fallback Mode active by default)

---

### 2. AD PLACEMENT & SDK MAPPING
Initialize the Unity Ads SDK during the application boot sequence using Unity Game ID: `6061517`. Explicitly map the ad formats to these specific Unity Placement IDs:
- Banner Ads -> `Shib_Banner_Android`
- Interstitial Ads -> `Shib_Interstitial_Android`
- Rewarded Video Ads -> `Shib_Rewarded_Android`

---

### 3. ADVANCED CONTROLLER WORKFLOW LOGIC (With Pre-loading Enhancement)

Implement a centralized Ad Controller utility or custom hook to manage the lifecycle of all ads. To ensure zero latency for the user, implement an aggressive background caching/pre-loading system for Interstitial and Rewarded ads from both networks simultaneously.

When an ad event is triggered by the user on any existing placement, evaluate the following runtime conditional logic tree:

- PHASE A: Check `force_unity_only` state from PocketBase.
  * IF TRUE: Completely bypass the AdMob pipeline. Directly invoke and display the respective Unity Ads Placement ID.
  * IF FALSE: Proceed to the Hybrid Fallback Mode (Phase B).

- PHASE B: Hybrid Fallback Mode Execution:
  1. Attempt to fire and display the pre-loaded Google AdMob ad instance.
  2. Race Condition Timeout: Set a strict 3-second recovery timeout wrapper around the AdMob initialization/load promise.
  3. IF AdMob successfully loads within 3 seconds -> Display the AdMob ad normally.
  4. IF AdMob triggers an `onAdFailedToLoad` error callback OR the 3-second timeout window expires -> Instantly catch the exception, terminate the AdMob request context, and immediately invoke the pre-loaded Unity Ad instance (`Shib_Interstitial_Android` or `Shib_Rewarded_Android`).

---

### 4. PLACEMENT-SPECIFIC COMPONENT IMPLEMENTATION

- For Banner Placements:
  Create a dynamic wrapper component for the existing banner slots. If `force_unity_only` is false, mount the AdMob Banner view. If its `onAdFailedToLoad` triggers, swap the child component context at runtime with the Unity Banner component mapped to `Shib_Banner_Android`. If the toggle is true, skip AdMob entirely and mount the Unity Banner.

- For Interstitial & Rewarded Placements:
  Wrap all execution blocks inside a clean `try/catch` sequence. If AdMob errors out or fails to return a valid instance, the catch block must fire the Unity asset show handler instantly so the user's reward or gameplay cycle is never broken or left lagging.

- Offline Failsafe:
  If the device is completely offline or the remote PocketBase fetch request fails, default the system local parameters gracefully to Hybrid Fallback Mode.
