---
name: PB admin-token REST routes must self-verify identity
description: /api/app/* Express routes call PocketBase under the admin token (bypassing collection rules) — money/mutation routes must verify the caller's PB token belongs to the target pbId, and guard atomic debits against TOCTOU.
---

- Express `/api/app/*` routes talk to PocketBase via `pbGet`/`pbPatch`/`pbHttp` using the ADMIN token (`getAdminToken`), which **bypasses ALL PB collection rules**. A route that takes `pbId` from the request body and mutates that user has NO identity check unless it adds one.
- **Rule:** any admin-token route that moves money or mutates another-user-spendable state MUST verify the caller: `pbHttp('GET', ` + "`/api/collections/users/records/${pbId}`" + `, null, token)` and assert `r.id === pbId` (same shape as the WS hub's `verifyToken`). Reject 401 otherwise. The client sends `token: pb.authStore.token` in the body.
- **Why:** the redeem route (`/api/app/hub/redeem`) was first added without this — any client could POST `{pbId,tickets}` to redeem *another* account's tickets. Loose existing REST routes (e.g. tournament `sync-points`) skip verification only because they don't touch spendable balance; do NOT use them as the security bar for money routes.
- **TOCTOU:** validate-then-atomic-`-` is NOT compare-and-swap. `users.hit_tickets` has no `min:0`, so two concurrent stale-read redeems both pass validation, both debit, and double-credit `shib_balance` while tickets go negative. Guard: after the atomic `{'hit_tickets-':n,'shib_balance+':shib}` write, if the returned `hit_tickets < 0`, reverse with `{'hit_tickets+':n,'shib_balance-':shib}` and fail (409). A stronger fix is `min:0` on the `hit_tickets` PB field so PB rejects the sub-zero write atomically (neither modifier applies).
- **Redeem convention:** Hit-Ticket redeem CREDITS the active wallet balance (`users.shib_balance`) directly via atomic PB modifiers — it NEVER creates a `withdrawals` row. Withdrawal is a separate, user-initiated, admin-approved step. `ensureWithdrawalRedeemMethod()` boot helper is kept only to protect any legacy `'Hit Ticket Redeem'` withdrawal records; legacy pending ones are not auto-migrated.
